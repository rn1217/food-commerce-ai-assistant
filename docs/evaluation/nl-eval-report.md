# 자연어 검색 평가와 프롬프트 v2 (2026-11-17)

기존 검증은 고정 질문 3개로, 일반 자연어 성능을 말할 수 없었습니다. 또 실제로 써 보면 "애매하게 물으면 상품을 못 찾는다"는 문제가 보였습니다. 이를 수치로 확인하려고 라벨을 붙인 평가셋을 만들고, 오답을 분석해 조건 해석 프롬프트와 출력 스키마를 고쳤습니다.

## 평가 설계

### 평가셋

| 이름 | 파일 | 문항 | 용도 |
| --- | --- | ---: | --- |
| dev | `data/eval_nl_queries.json` | 84 | 오답 분석과 프롬프트 수정에 사용 |
| holdout | `data/eval_nl_holdout.json` | 30 | v2 프롬프트 작성 시 참고하지 않은 표현으로 일반화 확인 |

dev 구성: 기본 12 · 복합 12 · 가격 표현 14 · 구어체 12 · 부정문 6 · 애매한 질문 14 · 미지원 조건 10 · 무관/공격 4.

- 각 문항은 **허용 정답 목록(accept)**을 가집니다. 응답 종류는 `search`(검색) / `clarify`(확인 질문) / `unsupported`(미지원 안내) 중 하나이며, 검색이면 7개 조건 필드 값까지 일치해야 정답입니다. "만원대"처럼 해석이 둘 이상 가능한 문항은 허용 정답을 여러 개 둡니다.
- 거절이 정답인 문항에는 지원 조건만 뽑은 `partial`을 적어, "지원 조건만으로는 보여줄 상품이 있었는지"를 따로 집계합니다.
- 받는 사람·상황(부모님, 명절)은 상품 조건이 아니므로 검색이 정답이라고 봤습니다. 반면 카테고리·보관 방법처럼 실제 상품 속성인데 지원하지 않는 조건은 현재 정책대로 미지원 안내를 정답으로 봤습니다.
- holdout은 dev와 같은 질문이 없고, v2 프롬프트에 들어간 예시 단어를 쓰지 않습니다. 이 결과를 보고 프롬프트를 다시 고치면 holdout의 의미가 사라지므로, 이후 수정은 dev로만 합니다.

### 측정 범위

- `app.query_service.interpret_query`를 그대로 호출합니다. 질문당 LLM 호출은 1회이며, 추천 이유와 FAQ 생성은 포함하지 않습니다.
- 응답 종류는 `app/main.py`와 같은 분기로 판정합니다.
- 상품 결과는 `data/products.csv`에 SQL과 같은 필터·정렬을 적용해 계산합니다. 서버와 DB 없이 실행할 수 있게 한 선택이며, 이 필터는 기존 실제 MySQL 평가의 수동 정답 15개와 같은 결과를 내는지 자동 테스트로 확인합니다.

### 지표

| 지표 | 정의 |
| --- | --- |
| 전체 정답률 | 허용 정답 중 하나와 응답 종류·조건 값이 모두 일치 |
| 검색/거절 판단 정확도 | 조건 값과 무관하게 응답 종류만 허용 정답에 포함 |
| 과잉 거절률 | 검색이 허용 정답인데 허용되지 않은 거절로 0건을 반환 |
| 잘못된 검색률 | 거절만 정답인데 조건을 무시하고 검색 |
| 결과 제공률 | 상품을 1개 이상 보여준 비율. 정답 여부와는 별개인 사용자 관점 지표 |
| 지연시간 p50/p95 | 조건 해석 LLM 호출 1회의 처리 시간 |

**오류 집계 원칙**: 네트워크·429·키 누락처럼 모델 판단과 무관한 실패만 정확도에서 제외합니다. `invalid_output`(모델 JSON의 스키마 검증 실패)은 모델 오류이므로 오답으로 셉니다.

### 실행

```powershell
.\.venv\Scripts\python.exe -m scripts.evaluate_nl --engine rule                     # 규칙 기준선(무료)
.\.venv\Scripts\python.exe -m scripts.evaluate_nl --engine llm --prompt v1           # 개선 전
.\.venv\Scripts\python.exe -m scripts.evaluate_nl --engine llm --prompt v2           # 개선 후
.\.venv\Scripts\python.exe -m scripts.evaluate_nl --engine llm --prompt v2 --dataset holdout
```

호출 사이에 4초씩 대기하고, 429가 나면 30초 뒤 한 번 재시도합니다. 결과는 `docs/evaluation/nl-eval-*.md`와 `.json`에 저장됩니다.

## 진행 과정

### 1. 규칙 기준선: Gemini가 실패하면 거의 아무것도 못 찾음

LLM 없이(`--engine rule`) 실행하면 dev 결과 제공률은 2.4%(2/84), holdout은 0%(0/30)였습니다. 장애 대비 규칙(`safe_rule_intent`)이 문장 전체가 정해진 형태일 때만 동작하기 때문입니다. "2만원 이하 상품"도 처리하지 못합니다.

즉 Gemini가 429나 시간 초과로 실패하는 순간, 사용자는 사실상 검색 결과를 받지 못합니다. 체감한 "못 찾음"의 일부는 이 경로였을 수 있습니다. 규칙을 넓히면 부정문을 놓칠 위험이 있어 이번에는 바꾸지 않고 기록만 남겼습니다.

- 결과: [nl-eval-rule-20261117-1414.md](nl-eval-rule-20261117-1414.md) · [nl-eval-rule-holdout-20261117-1451.md](nl-eval-rule-holdout-20261117-1451.md)

### 4. 오답 15건 분석

| 원인 | 건수 | 문항 |
| --- | ---: | --- |
| 상품 속성이 아닌 말을 미지원으로 분류 | 9 (60%) | b03 간식, c10 당도 1, k08 통으로 들어있는, k11 주머니 사정, a01 부모님, a02 회사 동료, a04 적당한 가격대, a09 명절, a11 가볍게 |
| 포장 조건 질문의 형식 오류(invalid_output) | 4 (27%) | b08, c05, k03, n06 |
| 라벨 경계 사례 | 2 (13%) | p10 "3만원 전후" → 27,000~33,000 검색, p14 "천원 이하" → 999 |

- **값 추출은 이미 정확했습니다.** 9건 중 7건은 지원 조건을 맞게 뽑아 놓고, 불필요한 미지원 항목 하나 때문에 0건이 됐습니다. v1 프롬프트는 "지원하지 않는 요구는 빠짐없이 적어라"고만 했고, 무엇이 상품 속성인지는 정의하지 않았습니다.
- **형식 오류 4건은 모두 포장 질문이었습니다.** v1은 포장을 `individual_only`와 `exclude_individual` 두 불리언으로 받고, 둘 다 true면 충돌 검증으로 거절합니다. 모델이 두 값을 동시에 true로 냈을 가능성이 높지만, 당시 원본 출력을 기록하지 않아 확정하지는 못했습니다.
- **라벨 경계 사례**: p10은 합리적인 해석이라 정답으로 볼 여지가 있고, p14는 '이하'를 미만처럼 처리한 오류지만 결과는 0건으로 같습니다. 개선 전후를 비교할 수 있도록 라벨은 바꾸지 않았습니다.
- 잘못된 검색 1건(p10)을 빼면, 미지원 조건을 무시하고 검색한 사례는 없었습니다.

### 5. 프롬프트 v2

| 변경 | 이유 | 대상 오답 |
| --- | --- | --- |
| LLM 출력의 포장 조건을 `packaging: any / individual / bulk` 하나로 통합 | 포함+제외 충돌을 스키마 차원에서 불가능하게 함 | 형식 오류 4 |
| unsupported의 정의 명시: 상품을 걸러내는 데 필요한 상품 속성만. 받는 사람·상황·이유·분위기·일반 명칭은 무시 | 과잉 미지원 분류 | 9 |
| 포장·당도·정렬의 동의 표현 규칙을 항목별로 정리 | "통으로 담긴", "당도 N인" 등 | k08, c10 |
| `invalid_output` 시 검증 실패 이유(`invalid_detail`)와 원본 앞 300자(`raw_output_preview`)를 로그·응답 메타에 기록 | 원인을 추측이 아니라 기록으로 확인 | — |
| 프롬프트 버전 관리(`LLM_QUERY_PROMPT_VERSION=v1/v2`, 메타에 `prompt_version` 기록) | 같은 코드로 개선 전후를 비교하고 ai_logs에서 버전별로 분석 | — |

- API 응답의 `conditions` 형식, SQL 인자, 부분 검색 금지 정책은 바꾸지 않았습니다. v2 출력은 기존 `SearchIntent`로 변환돼 같은 검증을 다시 거칩니다.
- v1 프롬프트는 2026-10-06 원본과 글자 단위로 같게 보존했습니다.
- 클래스 docstring이 JSON 스키마의 `description`으로 프롬프트에 들어가는 것을 발견해 주석으로 바꿨습니다. v1 프롬프트를 원본과 똑같이 유지하기 위한 조치입니다.

### 6. holdout 30문항 추가

dev 오답을 보고 프롬프트를 고쳤으므로, dev 점수가 오르는 것만으로는 일반화를 주장할 수 없습니다. v2 프롬프트를 쓸 때 참고하지 않은 표현(친구 생일, 집들이, 선생님, 출출할 때, 용돈, 벌크, 낱개로 소분, 한 상자 등)으로 30문항을 따로 만들었습니다. 자동 테스트로 dev와 질문이 겹치지 않는지 확인합니다.

## 해석 시 주의

- 가상 상품 30개, 개발자가 직접 붙인 라벨 기준입니다. 경계 사례의 판단은 주관이 들어갑니다.
- LLM 출력은 매 실행 달라질 수 있습니다. 위 수치는 각 1회 실행 결과이며, 반복 측정의 평균이 아닙니다.
- dev 점수 개선은 그 질문들을 보고 고친 결과(in-sample)입니다. 일반화는 holdout으로 판단합니다.
- 지연시간은 로컬 PC에서 외부 API를 호출한 시간이며, 무료 등급 상태에 영향을 받습니다.

## 남은 과제

- **부분 검색 정책**: v1 기준 9건은 지원 조건만으로 상품을 보여줄 수 있었지만 0건이었습니다(예: "선물용 견과류"는 선물용 19개). 지원 조건으로 검색하고 제외한 조건을 안내하는 방식을 검토합니다. 정답 기준이 바뀌므로 평가셋에 응답 종류를 추가해야 합니다.
- **일반 명칭 후처리와 회귀 수정**: '간식' 등 일반 명칭을 `unsupported`에서 제거하고, b07(정렬만 있는 질문)과 n05(선물 여부 무관) 회귀를 고칩니다. holdout 측정 후 진행합니다.
