# 2026-11-17 — 자연어 평가셋 구축과 프롬프트 v2

## 배경

새 PC에서 프로젝트를 다시 설치해 실행했다. 실행은 정상이었지만, 써 보면 애매한 질문에서 상품을 찾지 못하는 경우가 많았다. 기존 자연어 검증은 고정 질문 3개뿐이라 이 문제의 크기를 말할 수 없었다.

## 재설치 중 확인한 점

- Python 3.11 가상환경에서 `numpy==2.5.3` 설치가 실패했다. numpy 2.5.x는 Python 3.12 이상만 지원한다. `py -0`으로 확인하니 3.11만 설치돼 있었고, `py -3.12`를 지정해도 3.11로 venv가 만들어졌다. 3.12 설치 후 venv를 다시 만들어 해결했다. README에 요구 버전을 적었다.
- `Unknown database 'food_commerce'`는 접속 정보 오류가 아니라 `sql/schema.sql`을 실행하지 않아서였다. 인증은 이미 통과한 상태였다.

## 평가셋과 스크립트

- `data/eval_nl_queries.json`(dev 84문항)과 `scripts/evaluate_nl.py`를 추가했다. 문항마다 허용 정답(검색/확인 질문/미지원 + 조건 값)을 둔다. 상품 결과는 CSV에 SQL과 같은 규칙을 적용해 계산하며, 기존 수동 정답 15개와 같은지 자동 테스트로 확인한다.
- 규칙 기준선: dev 정답률 25.0%, 결과 제공 2.4%. Gemini가 실패하면 사실상 검색이 안 된다.
- 10문항 시험에서 `invalid_output`을 API 오류로 분류해 정확도 분모에서 빼는 집계 오류를 발견했다. 88.9%로 보였던 값이 실제로는 80%였다. 스키마 검증 실패는 모델 오류로 세도록 수정했다.
- dev 84문항(v1): 정답률 82.1%, 과잉 거절 22.0%, 결과 제공 54.8%, 형식 오류 4건, p95 12,789ms. 1회 실행이다.

## 오답 분석과 결정

- 오답 15건: 미지원 과잉 분류 9건, 포장 질문 형식 오류 4건, 라벨 경계 사례 2건.
- 값 추출은 거의 정확했다. 문제는 "무엇이 미지원인가"에 대한 정의가 없는 프롬프트, 그리고 포장을 두 불리언으로 받는 스키마였다.
- 프롬프트 v2: 포장 조건을 `packaging` 하나로 통합하고, 미지원 기준과 무시할 표현(받는 사람·상황·이유·분위기·일반 명칭)을 명시했다.
- v1은 원본 그대로 보존하고 `LLM_QUERY_PROMPT_VERSION`으로 전환하게 했다. 같은 코드로 전후를 비교하고 `interpretation.prompt_version`으로 로그를 구분하기 위해서다.
- 형식 오류의 원인을 추측하지 않도록 `invalid_detail`과 `raw_output_preview`(앞 300자)를 기록하게 했다. v1의 4건은 원본이 없어 원인을 확정하지 못했다.
- dev를 보고 고쳤으므로 dev 점수 상승은 in-sample이다. 프롬프트에 쓰지 않은 표현으로 holdout 30문항을 만들었다. 규칙 기준선의 holdout 정답률은 26.7%다.
- 부분 검색 정책은 이번에 바꾸지 않았다. 정답 기준 자체가 바뀌어 비교가 섞이기 때문이다. 영향(9건)은 평가 문서에 기록했다.

## 발견한 부수 문제

Pydantic 모델의 클래스 docstring이 JSON 스키마의 `description`으로 들어가 프롬프트에 포함됐다. v1을 원본과 똑같이 유지하려고 주석으로 바꾸고, v1 프롬프트가 원본과 글자 단위로 같은지 확인했다.

## 검증

- 로컬 Windows 가상환경에서 자동 테스트 66개 통과.
- dev 84문항 v2: 정답률 95.2%(v1 82.1%), 과잉 거절 6.8%(v1 22.0%), 형식 오류 0건(v1 4건). 문항별로 13개가 고쳐지고 2개(b07, n05)가 새로 틀렸다. 프롬프트 수정이 다른 질문을 망가뜨릴 수 있다는 것을 문항별 비교로 확인했다.
- '간식'은 프롬프트에 명시해도 미지원으로 분류됐다. 다음 수정은 코드 후처리로 한다.
- holdout(v1·v2)은 아직 측정하지 않았다. 회귀 수정은 holdout 측정 후에 한다.
